# Rewind 1.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 1.2.0 with five things: a resolution-change fix that actually holds, a silent update with no leftovers, Discord/GitHub buttons, four switchable profiles, and a written hardware-compatibility report.

**Architecture:** The display fix restarts the replay chain around OBS's video-context reset, because OBS refuses that reset while an output is active. The updater keeps electron-updater and NSIS but installs silently and prunes its cache. Profiles are a 4-slot overlay on the three settings that matter (buffer length, fps, quality), applied through the rebuild tiers that already exist. The report is a document; no runtime code.

**Tech Stack:** Electron 30, React 18, TypeScript, obs-studio-node 0.25.77, electron-updater 6, electron-builder 25, koffi, uiohook-napi. No new dependencies.

**Spec:** this file (decisions below), plus `ISSUES.md` entries "Display resolution changes mid-capture" and "The updater cache is never pruned", and `docs/superpowers/plans/2026-10-14-klip-derived-optimizations.md` for the engine facts.

## Global Constraints

- No new runtime dependencies. Windows x64 only.
- The offline promise holds: no network call unless the user clicks. The update check stays manual; nothing polls.
- Verify by measurement (logs, ffprobe dimensions, process/file lists, byte counts), never by a plausible screen.
- A user-paused buffer stays paused across every change in this plan.
- Gates per task, all must be green before the commit: `npm run typecheck`, `npm run build`, `node scripts\utf8-audit.mjs`, `node scripts\channel-check.mjs`, and `npm run test:ui` when renderer files changed.
- One commit per task, conventional message. Work in place on `main`.
- Packaging writes to `release/`; if OpenChamber holds `release\app.asar`, package to `%TEMP%\rewind-build` instead (a restart of OpenChamber clears it).

## Review Focus

1. A resolution change while a continuous recording runs — the recording must be finished and registered, never silently dropped.
2. A resolution change while the buffer is user-paused — the canvas must still sync and the buffer must stay paused.
3. A burst of display events (Windows emits several per change) — one sync, no interleaved restarts.
4. An interrupted or repeated update — leftovers must never be treated as a ready update, and the cache must be empty after a successful start.
5. A profile switch to a slot the machine cannot hold (120 fps on weak hardware), and a switch while recording — the switch must fail loudly or finish the recording cleanly.

- [ ] **Step 3: Implement `applyDisplayChange()`**

In `capture.ts`, replacing `syncCanvasToDisplay()`:

```ts
async applyDisplayChange(): Promise<{ from: string; to: string } | null> {
  if (!this.obsCore.isInitialized?.()) return null
  if (!this.obsCore.syncCanvasToDisplay) return null

  const buffer = this.replayBuffer
  const wasActive = buffer?.isReplayBufferActive?.() === true
  if (wasActive) await buffer.stopReplayBuffer(true)
  try {
    const result = this.obsCore.syncCanvasToDisplay()
    if (!result.changed) return null
    const to = this.refreshCanvasForDisplay()
    return { from: `${this.canvasWidth}x${this.canvasHeight}`, to: `${result.base.width}x${result.base.height}` }
  } finally {
    if (wasActive) await buffer.startReplayBuffer(true)
    const finished = buffer?.takeFinishedOnTeardown?.() ?? null
    if (finished) this.onRecordingFinished?.(finished)
  }
}
```

Notes that must hold:
- Order is stop → reset → refit → start. The refit only runs when `result.changed`.
- `stopReplayBuffer(true)`, never `pauseReplayBuffer()`: the pause flag is the user's, and this is not the user pausing.
- `onRecordingFinished` is a constructor callback wired in `index.ts` to `registerFinishedFromBufferStop`, so a recording cut by the restart lands in the library.

- [ ] **Step 4: Serialize and re-run bursts**

The listener already debounces 750 ms. Add an in-progress guard in `index.ts`: while `applyDisplayChange()` runs, a further event sets a `pending` flag, and one more run happens after it finishes. Run it through `services.capture.acquireSourceLock(...)` so it cannot interleave with a source switch.

- [ ] **Step 5: `display-added` syncs too**

Remember `screen.getPrimaryDisplay().id` at startup. In the `display-added` handler, if the primary's id changed, run the same sync path (today it only invalidates the device cache — this is the gap in `ISSUES.md` "Known gap in that fix"). `display-removed` keeps the cache invalidation only.

- [ ] **Step 3: The model**

```ts
profiles: [
  { name: 'Balanced', bufferDuration: 60, fps: 30, visualQuality: 'high' },
  { name: 'Long buffer', bufferDuration: 120, fps: 30, visualQuality: 'standard' },
  { name: 'Smooth', bufferDuration: 30, fps: 60, visualQuality: 'high' },
```

- [ ] **Step 4: `src/main/profiles.ts`**

`applyProfile(index)`:

1. Validate the index; read the target profile (clamped).
2. Diff against the live settings: `fpsChanged`, `qualityChanged`, `durationChanged`.
3. Write all three settings plus `activeProfile` in one pass.
4. Apply once, heaviest first: `fpsChanged` → `reinitPipeline('Applying profile …', { preservePaused: true })`; else `qualityChanged` → `replay().rebuildAndRestart()`; else `durationChanged` → `replay().setBufferDuration(n)`; else nothing.
5. On failure, restore the previous settings and rethrow (the same contract as `applyEncoderSetting`).

`captureActiveProfileValues()` copies the live `fps`/`visualQuality`/`bufferDuration` into `profiles[activeProfile]`. Call it from `ipc.ts` after a successful `applyEncoderSetting` for those keys, and from the buffer-duration handler — so an edit in Settings belongs to the profile that is active, and switching away and back keeps it.

- [ ] **Step 1: Write the report**

Sections, every claim labelled **measured here** / **vendor docs** / **needs a machine**:

1. **Capture paths** — DXGI desktop duplication (`monitor_capture`, method automatic), WGC (`window_capture`), game hook (`game_capture`, Win11 22H2+).
